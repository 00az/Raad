### Notes

- ADR-006 and ADR-007, recorded as Proposed without a question, are sound and the usual choices for this problem; each names two rejected alternatives and has a security section. ADR-006 is safe to accept once its store requirement carries the uniqueness conditions in the first finding. ADR-007 is safe to accept once its consequences say that account actions do not pass the platform's firewall.
- Hand-offs the design records for later stages: the signal wiring, the Ledger store's all-or-nothing change, and whether the two stores share one database (infrastructure design); how the email and display name reach MoneyApi on the safety-net path (Contract Design); the transfer reference format (Functional Design); a unit of its own for the platform (Units Generation); updating WalletDirectory if profile edits are ever added (ADR-002). The findings above add the hand-offs that are missing.
- Transfer holds only wallet ids, while WalletDirectory is keyed by user id, so the Ledger's history page has to return each other party's owner id for MoneyApi's batch lookup. Worth stating for Contract Design.
- `interaction-spec.md` Flow F1 step 4 and `mockups.md` S3 still say the money service creates the wallet at the first sign-in. What the user sees is unchanged, but the text now differs from ADR-003.
- ADR-001's Context credits `team-practices.md` with "the lookup of people by email", which that file does not say.

### Summary

The catalogue is well-formed and the money core (Ledger, ADR-006) is sound, but three gaps should be settled before approval: the store requirements leave out the uniqueness checks that prevent double moves and double wallets under simultaneous calls; the account-confirmed signal needs a wiring across repos that ADR-005 and the deploy-first practice leave without a clean path, and Q1 B was chosen before that cost was visible; and FR1.6 has no owner, which can leave a confirmed user permanently without a wallet.
