### Notes

- Edges that hold: U2 on U1, U3 on U1, U4 on U1 and U3 on U2 (Q2 B) are real code or test needs. U3 on U4 is real too: U3's account tests run against the password rule (A4), code resend and session settings that U4 adds to U1's sign-in pool.
- U3's `ui` kind gives it a functional spec and frontend components but no entities or rules files. The three app entities (PendingTransfer, BalanceSnapshot, LanguageSetting) and the request-key rules behind US3.6 and US3.8 will have to live in U3's functional spec; a line in U3's implementation notes would keep them from being missed.
- U1 calls the Contract Design description the source of truth but does not say which description it commits to `RaadMoneyService`, or that U1's app generates its Dart client from it as the practices require; U2 commits "the complete" one. Saying so avoids a hand-written client in U1 that U3 later replaces.
- U1 places "the public API address with the `/money` path" in `Raad`, which deploys first. If `Raad` creates the `/money` mapping, it needs the money service's API before that exists. Saying that the money service attaches `/money` to the platform's address keeps the platform first and keeps the U2-on-U4 dependency one way.
- U1's cell in the Components and Units table lists "a basic firewall", which U1's responsibilities and the approved plan do not.
- U1 differs from the Walking Skeleton list in `stories.md`: US1.1 sign-up is out (Q3 A), and parts of US3.2, US3.4, US4.2 and US6.4 are in. One sentence in the Walking Skeleton section would save Delivery Planning from reconciling the two.
- The move of US6.2 and US6.4 into units, against the approved plan, is explained in the story map; its effect on U2 and U4 is part of the first Major finding. The R-01 to R-08 rows otherwise match the units' responsibilities.

### Summary

The edge block, unit table, story map and traceability table are well-formed and agree with each other, U1 is a real integrated slice once its checks open both test wallets, and no build order or critical path is named. Before approving, the person should weigh that U2 needs U4 for its `stg` and `prd` stacks and for the account-confirmed signal, whose wiring has no owner, although the graph has no edge between them, and that `packaging` leaves U4's seven stories and its sign-in and signal rules without a functional design.
