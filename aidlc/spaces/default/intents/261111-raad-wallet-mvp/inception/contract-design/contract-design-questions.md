# Contract Design: Questions

Conversation language: English.

Contract Design fixes what crosses each boundary, who owns the specification, and what happens when a call or message fails. The main public boundary is the money API consumed by `RaadMobile`. The main inter-unit boundary is account confirmation from the shared platform (`Raad`, U4) to the money service (`RaadMoneyService`, U2). The shared-code edges from U1 to later units and U5's practice-only edge need no network contract.

Each question suggests an answer marked "(Recommended)". The trade in brackets only says whose call it usually is; anyone can answer any question.

## Q1. [Architect] How should account confirmation reach the money service?

Domain Design says the sign-in service starts wallet setup when an account is confirmed, with the first signed-in money request as a safety net. The platform deploys before the money service in each environment, so a direct call can fail while the money service is absent. The platform already includes a shared event bus.

A. Publish an asynchronous `UserConfirmed` event to the shared event bus. U4 owns the event schema; U2 subscribes in the same environment. Delivery is retried, duplicates are safe, and failure never delays or fails account confirmation. This is a narrow exception to ADR-005; transfer-completed events remain out of the MVP. (Recommended: no deployment-time dependency from the platform to the money service.)
B. Make a direct private HTTPS call from the sign-in service to a wallet-setup endpoint owned by U2. A failed call is logged and not retried; the first signed-in money request remains the safety net.
C. Remove the confirmation signal and use only the first signed-in money request. This changes the earlier Q1 B decision but removes the cross-unit contract.
X. Other (please specify)

[Answer]: A (all recommended; **Mode:** chat)

## Q2. [Architect] How should the public money API be versioned?

The shared public API routes the `/money` prefix to the money service. A version in the path lets a future breaking contract coexist with the MVP.

A. REST over HTTPS with JSON, under `/money/v1`. Additive changes stay in v1; a breaking change gets `/money/v2`. Consumers ignore unknown response fields. (Recommended)
B. REST over HTTPS with JSON under `/money`, with versioning only in a request header.
C. GraphQL at `/money/graphql`.

## Q3. [Architect] Who owns the money API description and generated client?

The team practice says each service's OpenAPI description lives in that service's repo and is the source of truth; the app generates its Dart client from it.

A. `RaadMoneyService` owns and releases `openapi/raad-money-v1.yaml`. `RaadMobile` pins an exact released revision and generates its Dart client in CI. A pull request that changes the description must pass compatibility checks before merge. (Recommended)
B. Copy the description into both repos and update both copies together.
C. `RaadMobile` owns the description because it is the only MVP consumer.

## Q4. [Architect] How should transfer retries carry the unique request key?

The key must be supplied on every transfer and reused only for the same locked recipient and amount after a lost answer.

A. A required `Idempotency-Key` HTTP header, generated by the app. The same signed-in user and key with identical details returns the first outcome; the same key with different details returns a conflict error. (Recommended)
B. A required `requestKey` field inside the JSON body, with the same behavior.
C. The money service creates the key. The app sends no key.

## Q5. [Architect] How should history pagination work?

A history page must stay stable when a new transfer arrives while the user loads later pages (AC4.3.2).

A. An opaque cursor returned as `nextCursor`. The app sends it unchanged; it expires after 24 hours, and an invalid or expired cursor returns a specific error that tells the app to refresh from the first page. Page size is 20, with a maximum of 100. (Recommended)
B. Page numbers (`page=1`, `page=2`) with 20 entries per page.
C. Timestamp pagination (`before=<time>`) with 20 entries per page.

[Answer]: A (all recommended; **Mode:** chat)

## Q6. [Architect] What error shape and retry rule should every money endpoint use?

The app needs stable codes while messages can be translated. A retry must never repeat a side effect accidentally.

A. JSON errors contain `code`, `message`, `correlationId` and optional field errors. The app decides by `code`, not the English message. It retries reads once after a timeout or server error; it retries a transfer only when the user chooses Try again, using the same idempotency key. Validation, authentication, authorization, low-balance and conflict errors are never retried automatically. (Recommended)
B. Use HTTP status and a plain message only. The app does not retry automatically.

## Q7. [Security engineer] How should the money API identify and authorize the caller?

The app must never choose which wallet it acts on. The money service receives a signed token from the shared sign-in service.

A. The app sends `Authorization: Bearer <access token>`. The public API and MoneyApi verify it, and MoneyApi takes the user ID only from the verified token. Wallet, transfer and history requests contain no caller user ID or source wallet ID. (Recommended)
B. The app sends the access token plus its user ID in each request; MoneyApi checks that they match.
