### Evidence and Boundaries

The selected GetUser adapter matches [AWS's documented authorization model](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_GetUser.html): it uses the signed-in user's access token with the SDK scope rather than IAM permission. The code retains issuer/client/token-type/signature/expiry checks, requires the exact scope, uses bounded single-attempt network configuration and checks returned identity and verified profile fields. The summary explicitly records the requested correction to the earlier OAuth/PKCE selection and preserves actual-provider checks as incomplete.

The origin restriction matches [CloudFront's documented custom-header behavior](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/add-origin-custom-headers.html): the configured origin header replaces a viewer's value. Caching remains disabled and both origins carry the credential. The runtime uses a 60-second cache and fails closed after expiry when retrieval fails. The summary accurately states that CloudFront configuration readers are trusted, automatic rotation is not implemented, and secret-only rotation does not update the distribution's resolved header. Its proposed deployment probes test missing/counterfeit direct-origin requests and successful CloudFront header replacement without exposing the credential.
