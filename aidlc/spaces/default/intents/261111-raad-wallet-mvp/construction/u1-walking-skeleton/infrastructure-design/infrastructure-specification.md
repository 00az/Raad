# Infrastructure Specification — U1 Walking Skeleton

Conversation language: English.

## Deployment

| Facet | Choice | Rationale |
|---|---|---|
| Compute model | AWS Lambda with Python for the platform edge adapter, MoneyApi and a platform telemetry processor. Ledger and WalletDirectory remain modules in RaadMoneyService, not network services. The telemetry processor has stream-ingestion and scheduled aggregation modes and never changes money data. | Stateless, bounded request handling fits dev load. The edge adapter owns routing/C5 checks; MoneyApi independently verifies tokens. CloudFront, rather than the adapter handler timer, supplies the complete public-duration measurement. |
| Networking topology | Regional API Gateway HTTP API behind a CloudFront distribution with AWS WAF. CloudFront is the public TLS edge; API Gateway routes the money path to the platform edge adapter. The adapter forwards the C1 request and original access token to the MoneyApi integration over authenticated HTTPS. No public database access, VPC, NAT gateway, queue or extra region is introduced for U1. | Keeps one public domain and a basic firewall while avoiding always-on network infrastructure at the demo scale. The exact adapter-to-MoneyApi integration must preserve C1 and is covered by the edge/service contract test. |
| Storage strategy | Three DynamoDB tables in the same account and region: Ledger for wallets and lookup metadata, dedicated Transactions for immutable completed transfers, and WalletDirectory for personal attributes. RaadMoneyService owns all three through its Ledger/directory boundaries. Use on-demand capacity, encryption at rest, TLS, and PITR disabled in disposable dev. | The canonical transfer exists once, keyed by transferId. A cross-table DynamoDB transaction keeps the money write atomic. No cache, replica or duplicate transfer-payload store is introduced. Dev rebuild remains an explicit action. |
| Ledger item layout | One wallet balance item per wallet partition, an owner-to-wallet uniqueness item, and small history lookup entries containing only transferId and ordering metadata. Lookup partition is the wallet ID; sort key is fixed-width UTC completedAt followed by transferId. Do not copy amount, reference, parties or profile payload into the lookup entries. Wallet opening conditionally creates the owner key and opening balance together. | Strongly consistent bounded base-table queries select transfer IDs for the caller's first page. The lookup entries are an index into Transactions, not independent transaction records or another source of transfer details. |
| Transactions item layout | Environment-specific dedicated table with string partition key transferId (UUID) and no wallet-ID primary key. Each immutable row contains transferId, reference, senderWalletId, recipientWalletId, integer amountHalalas, currency SAR and completedAt. No personal attributes, TTL, request key or replay outcome in U1. Insert condition requires transferId not to exist. | Implements ADR-008 and C1. U1 provisions this table. U2 adds sender/recipient history indexes and saved TransferRequest outcomes; both parties continue to read the same canonical transfer. |
| Transfer write | One TransactWriteItems call across Ledger and Transactions: conditional sender debit, recipient credit, immutable transaction insertion, sender lookup insertion and recipient lookup insertion. Both wallet updates carry their own conditions; no separate ConditionCheck targets an updated item. Disable SDK write retries and preserve the U1 uncertain-result/no-resubmit rule. | All five item actions commit or abort together. The canonical row and index references cannot be partially created by this operation. U2 later includes its successful saved outcome in the atomic operation without changing transaction identity. |
| First-page read | Resolve the caller's wallet, strongly query its lookup partition descending with at most limit plus one lookahead, then strongly BatchGet the selected Transactions IDs and batch counterparty profiles. Fetch at most 100 canonical rows for a page, not its lookahead. Reorder unordered batch results by the query keys; validate each row involves the caller's wallet. | No table scan, whole-history load or GSI read-after-write assumption. Bound UnprocessedKeys retries with backoff inside the existing read deadline; return a safe page error on exhausted retries, a missing canonical row or inconsistent ownership instead of silently omitting transfers. U2 owns later-page navigation and indexes. |
| WalletDirectory item layout | Store holder attributes separately from Ledger. Enforce unique user ID and normalized email with conditional transactional writes to holder and email-key items. Resolve recipient email by exact normalized key; batch distinct counterparty lookups for history. | Preserves the approved data boundary and bounded lookup requirements. Directory registration remains independently retryable after wallet creation and never credits money. |
| Environments | Separate dev, stg and prd resources and configuration. This Unit provisions and verifies dev only. Use the same CDK definitions with environment parameters. Use separate user pools, API hostnames, data tables, secrets and log groups per environment. | Prevents cross-environment token and data use. Production availability, recovery and retention remain later environment obligations. |
| Infrastructure as code | Python AWS CDK in each owning repository, versioned with the service. `Raad` owns the shared user pool, public domain/certificate, CloudFront/WAF, API Gateway and edge adapter. `RaadMoneyService` owns MoneyApi, Ledger, WalletDirectory and their execution roles. `RaadMobile` consumes generated environment configuration and the pinned C1 client. | Matches the affirmed repo responsibilities and keeps each repo's deployment independent. Do not introduce another IaC framework or runtime. |
| Resource sizing | Start the MoneyApi and edge adapter at 20 maximum concurrent requests each in dev, with bounded downstream client connections and no in-process queue. DynamoDB starts on-demand. Measure the configured maximum and downstream envelope before the accepted load run; do not increase it from a failed run without repeating the atomicity and load checks. | Maps the 20 admitted-request proposal to a candidate setting, not a throughput or p95 claim. Ten active users and the two-read path are the validation workload. |
| TLS and encryption | TLS 1.2 or later on mobile-to-edge, edge-to-MoneyApi, Cognito profile calls and AWS service calls. Encrypt DynamoDB tables, Secrets Manager secrets and CloudWatch log groups at rest. IAM roles grant only required table operations, parameter/secret reads and telemetry writes. | Implements the approved transport, persistence and least-privilege requirements. |

## Infrastructure Services

| Service | Role | Configuration | Notes |
|---|---|---|---|
| Amazon Cognito User Pools | Identity | One shared pool per environment; public mobile app client without a client secret; the existing native SDK sign-in flow with environment-specific issuer/client_id audience and access-token type binding. Use bounded Cognito GetUser compatible with SDK token scope; independently verify JWT then returned subject/verified email. Do not require OAuth userInfo-only scopes. | P1, P2 and P13 capability checks must pass on dev. P7 earlier-code invalidation is unverified. AWS does not expose a pre-confirmation trigger to invent as a fallback; if native behavior fails, block identity release and revisit C3 with the person. No identity pool is needed because the mobile app does not call AWS services directly. |
| Amazon CloudFront | CDN / public edge | Serve the API domain over HTTPS and forward required C1 headers/body/path to the regional API Gateway HTTP API. Disable authenticated-route caching. Attach a 100%-sampling real-time log configuration to the configured transfers cache behavior, selecting only monitoring-design.md's seven safe fields and sending to the platform telemetry stream. | Preserve C1. The native time-taken field includes outer processing and origin initialization; log delivery is best effort and acceptance requires request-level reconciliation. |
| AWS WAF | Firewall | Associate a CLOUDFRONT-scope web ACL, managed through us-east-1, with the distribution. Enable AWS managed common protections and a conservative IP-based rate rule for basic U1 protection. Log only safe rule metadata. | Full per-caller rate policy is later U4 work. Validate that WAF blocks do not expose request bodies or credentials. |
| Amazon API Gateway HTTP API | API gateway | Regional API with the C1 `/money/v1` route, AWS-generated HTTPS origin hostname and Lambda integration to the platform edge adapter. Set bounded request/response timeouts and payload limits compatible with C1. | The edge adapter, rather than a built-in JWT authorizer, performs the required independent C5 verification and C1 error/correlation mapping. This permits controlled 401, 429 and 503 response bodies. |
| Platform edge adapter | Other | Python Lambda owned by `Raad`; verify the configured Cognito token profile and key cache, strip spoofed identity headers, preserve or create the correlation ID, compute the shared protected correlation key, forward the original token and C1 request, and map upstream failures to safe C1 errors. Maximum concurrency 20 for dev. | Requires an integration that reaches MoneyApi over authenticated HTTPS and returns C1 status/body without logging payloads. Prove this path end to end before claiming C5 support. |
| AWS Lambda | Compute | Python Lambda for MoneyApi in `RaadMoneyService`, with a separate execution role, seven-second service deadline, bounded outbound concurrency, no automatic retries on transfer writes and concurrency capped at 20 in dev. | Keep Ledger and WalletDirectory inside the service process behind separate data-access ports; only Ledger's transaction adapter mutates balances. |
| Amazon DynamoDB | Database | Ledger, dedicated Transactions and WalletDirectory tables; on-demand billing, PITR off only in disposable dev, encryption at rest, deletion protection off only for dev, no TTL on balances, completed transfers or lookup entries. Transaction adapter permissions cover only the required actions on these environment-specific tables; ordinary request handling has no update/delete path for completed Transactions rows. | Use cross-table transactional writes for balances, one canonical row and reference indexes. Strong base-table Query plus consistent BatchGet serves the first page. U1 creates no saved business idempotency outcome; U2 extends the transaction for that guarantee. |
| AWS Secrets Manager | Secret store | One environment-specific secret for test-user credentials and one environment-specific shared correlation HMAC profile. Secret values are read at runtime by named roles; GitHub Actions receives no long-lived AWS credentials. | Keep email addresses and secret values out of source control, logs, CLI arguments and dashboards. |
| AWS KMS / service encryption | Key management | Use AWS-managed encryption for DynamoDB and Secrets Manager. CloudWatch Logs uses its default service-side AES-GCM encryption at rest; do not assume an AWS-managed KMS alias exists for log groups. Restrict secret access to the owning runtime roles. | No customer-managed key is required by the approved dev design. Production key policy and recovery remain later review items. |
| Amazon CloudWatch | Monitoring | Explicit 14-day retention on every dev log group; custom low-cardinality metrics; dashboard and three sample-gated alarms described in `monitoring-design.md`. | Caller correlation IDs, wallet IDs, transfer IDs, email and display name are not metric dimensions. |
| Amazon Kinesis Data Streams | Telemetry transport | One environment-specific encrypted stream in us-east-1; initial one-shard dev setting and 24-hour retention, validated under the demo workload. CloudFront's account-scoped service role can write only this stream; the telemetry Lambda can consume it. Configure the relevant KMS permissions for encrypted delivery. | Carries only the selected safe access-log fields. No business transfer, request body, sign-in token or C2 confirmation event enters this stream. Track throttling and consumer lag; delivery failures do not block or retry money operations. |
| Platform telemetry Lambda | Monitoring processor | Python Lambda in Raad, separate execution role and bounded concurrency (initial 2). Stream mode validates and writes safe CloudFront records to a dedicated 14-day CloudWatch log group. Scheduled mode queries only that group, deduplicates native request IDs, evaluates consecutive event windows and publishes bounded aggregate metrics. Finite per-query/processing deadlines; no table or money-service invocation permissions. | Implements monitoring-design.md's public-boundary measurement, not distributed tracing. Failed, truncated or stale collection produces insufficient data; the handler's own duration is not the API latency SLI. |
| Amazon EventBridge Scheduler | Monitoring schedule | Environment-scoped five-minute schedule, two minutes after each boundary, invoking the telemetry Lambda's aggregation mode. Restrict its invocation role to this processor and scope trust to this account/schedule. | Collection grace is a local operating setting, not a guaranteed CloudFront delivery bound. Duplicate invocations must not multiply observed sample counts. |
| Amazon SNS | Notification | One environment-specific topic subscribed to the team monitored email address supplied through deploy configuration; send on alarm entry and recovery only. | Confirm email subscription and test delivery before recording monitoring evidence. The address is not committed to the repository. |

## Capability Checks and Open Inputs

- Before implementation, verify Cognito's C3 capabilities P1, P2 and P13 in dev, including issuer, audience, profile attributes and the selected own-profile source. Determine P7 resend behavior. No unsupported trigger fallback is selected; U4 infrastructure-specification.md records the capability gap and release block.
- The real dev/stg/prd API hostnames, user-pool IDs, issuer URLs, app-client IDs, CloudFront certificate details and team notification email are environment inputs. They are generated or supplied during provisioning; do not invent or commit them.
- Define the shared correlation profile as a random 256-bit HMAC-SHA-256 key in an environment-specific Secrets Manager secret. The platform owns creation and versioning; edge and MoneyApi receive read-only access. Emit `correlationKeyVersion` and the hex HMAC of the caller correlation ID in both services. Keep the current and immediately previous key versions available for the 14-day log-retention window; rotation changes the active version only after both runtimes can read it. Never log the raw correlation ID or key.
- Deploy `Raad` shared identity and public-edge resources first, deploy the MoneyApi service and tables next, then publish the service integration/configuration and regenerate the mobile environment file. During the gap, the public route returns a safe unavailable response; it does not claim readiness.
- Dev rebuild is manual and may lose simulated history. Recreate test users through Cognito and initialize both wallets through supported C1 setup; do not insert fixtures directly into tables. Rollback redeploys the prior known-good repo commit and reruns the smoke check; it does not restore lost data.
- Implement the current approved Functional Design: PUT wallet setup repairs a missing holder entry after wallet commit, GET never opens a wallet, public shapes follow C1, monetary input uses integer text parsing, history has a deterministic timestamp/ID tie order, and each API/iOS/Android journey has its own fresh prepared pair.

## Data Transition and Cost Handoff

| Concern | Design and release condition |
|---|---|
| Existing wallet-keyed transfer payloads | Inspect the deployed schema before release. If the old layout has data, create Transactions additively and quiesce dev transfer writes during a controlled migration. Group old entries by transferId, validate paired records agree on both wallets/amount/reference/time, conditionally insert one canonical row, and convert old history entries to reference-only index entries. Reject mismatches for investigation. Do not change balances, create opening credits or silently discard unmatched records. |
| Activation and rollback | Compare unique transfer counts, reference resolution, each wallet's balance and both history views before enabling the new writer. Route traffic to the new version only after these checks pass. After cutover, rollback code must understand the canonical layout; do not reactivate a legacy writer that only writes wallet-keyed payloads. A dev reset is a separate explicit engineer decision, not this migration's fallback. |
| U2 extension | Keep transfer IDs and canonical rows stable. Add sender/recipient indexes and outcome persistence through additive changes, test index consistency/paging before switching history reads, and retain working reference lookups until the replacement has passed verification. Do not fabricate outcomes for historical U1 keys. |
| Cost inputs | One completed U1 transfer performs five transactional item writes and a first-page read performs one bounded lookup query plus canonical/profile batch reads. Estimate requests/storage from measured sizes and demo workload; include Lambda, API Gateway, CloudFront/WAF real-time logging, the telemetry Kinesis stream, scheduled processing/Logs Insights queries, Cognito, Secrets Manager and CloudWatch/SNS. Account for the stream's provisioned shard cost even when idle. Tag by project, environment and owning service. No monthly traffic or dollar budget has been supplied; report the workload-based estimate before provisioning rather than inventing a monthly figure. |
