# CI/CD Pipeline — U1 Walking Skeleton

Conversation language: English.

## Pipeline Stages

Each repository keeps an independent GitHub Actions pipeline. Pull requests are required for every change; CI runs the same checks locally and in GitHub Actions. Each workflow authenticates to AWS through GitHub OIDC and a short-lived, environment-scoped role. No static AWS keys or test credentials are stored in repository secrets.

1. **Source and contract check** — check out the repository, validate the pinned contract files and SHA-256 entries, and fail if the generated-client pin is stale.
2. **Lint and type checks** — Python repos run Ruff and strict mypy; the Flutter repo runs `dart format --set-exit-if-changed` and `flutter analyze` with the affirmed lint rules.
3. **Build and unit tests** — install from committed lockfiles; Python uses the supported pinned runtime, `uv`, pytest and Hypothesis; Flutter uses `flutter test`. Enforce 80% line coverage in each backend/mobile repo and 95% line and branch coverage for the Ledger money core. Ledger rule changes follow the affirmed test-first order.
4. **Security and dependency checks** — run secret scanning, dependency audit and the repository's existing security checks. Fail on high/critical findings; never print test credentials, request bodies or unfiltered SDK exceptions.
5. **Infrastructure synthesis and assertions** — in `Raad`, synthesize Python CDK, run CDK security checks and assert TLS, WAF association, no authenticated-route caching, log retention, encrypted resources, scoped IAM and environment separation. In `RaadMoneyService`, assert three distinct tables (Ledger, Transactions, WalletDirectory), Transactions' transferId primary key, encryption, no money/history TTL, environment-scoped transaction/read permissions, bounded Lambda concurrency, deadlines and no transfer-write retry. Review the CDK diff for resource replacement or deletion before deploying the additive table change. Do not deploy from an unreviewed pull request.
6. **Contract and integration tests** — validate request and response shapes against the pinned partial C1 pre-release; exercise edge forwarding, spoofed identity-header removal, correlation behavior, safe error mapping and the independent MoneyApi verifier. Run real local DynamoDB tests of the five-action Ledger/Transactions commit, conditional uniqueness, conservation, non-negative balances, distinct transfers between the same wallets, one canonical row per transferId and two reference-only lookup entries. Inject transaction failure and verify neither balances nor canonical/index records partially change; verify both users' histories resolve the same transfer. Test bounded strongly consistent Query/BatchGet, deterministic response reordering, unprocessed/missing rows and no silent omission. U1 stores no business replay outcome; test that uncertain results cannot be resubmitted. Mock-only success is not transaction evidence.

   **Public timing checks:** assert CloudFront real-time logging uses 100% sampling and exactly the safe field allowlist; encrypted telemetry delivery, separate no-money-access processor role, log retention and bounded schedule are present. Test duplicate/malformed/delayed log records, query limits, consecutive-window aggregation and missing-data behavior. In deployed dev, use a separate controlled fixture with an adapter initialization delay above two seconds, plus a pre-handler origin delay, to prove the native CloudFront duration includes time the handler timer omits. Join every probe by the native CloudFront response/request ID, exercise both slow and recovery alarm windows, and prove missing logs block acceptance. Remove all delay injection before normal checks. Component percentiles or Lambda timing cannot substitute for public latency.
7. **Merge and dev deployment** — after all checks pass and the other engineer approves, squash-merge to `main`. Deploy the shared `Raad` resources first, then `RaadMoneyService`, then publish the environment configuration consumed by `RaadMobile`. If the MoneyApi integration is not ready, the public route returns a safe unavailable response. A successful infrastructure deployment alone does not mean the end-to-end skeleton works.
8. **Dev verification** — prepare independent fresh API/iOS/Android fixture pairs; sign in and initialize both parties with PUT /wallet and confirm directory readiness before sending. Run `scripts/verify-dev.sh` against real dev sign-in, API and store. Verify the completed transaction ID in both histories and one canonical Transactions row, without reusing an uncertain send. Run the separate accepted performance check with an isolated 100-user population, 10 active users, at least 200 valid funded transfers and the full cold-plus-sustained sample population. Capture safe outputs and all three repo commit IDs.
9. **Staging and production promotion** — use the same CDK definitions with isolated configuration. Promote dev-verified commits through stg, then prd, without environment branches. Production remains behind a manual approval; validate production retention, availability measurement, backup/recovery and security requirements before first release. These environments are outside this U1 dev provisioning run.

## Stage-to-Gate Map

| Stage | Gate |
|---|---|
| Pull request validation | All applicable lint, type, build, test, coverage, security, contract and CDK checks pass; second engineer approves. |
| Dev deployment | Short-lived OIDC role and required environment parameters are present; deploy shared platform, then MoneyApi; fail closed on missing issuer/audience/secret configuration. |
| Dev smoke and skeleton verification | `scripts/verify-dev.sh` passes against the real dev path; both users are initialized through C1; setup readiness, balance, one transfer and history are verified. |
| Performance acceptance | All test attempts are accounted for and every response is reconciled to one deduplicated CloudFront time-taken record. Combined idle-start/sustained and sustained public-duration p95 are each at most 2,000 ms, and every valid funded transfer succeeds. Missing public records, no-response attempts, conflicting duplicates or unavailable telemetry prevent a pass; preserve client elapsed times, coverage and phase labels separately. |
| Staging promotion | Dev evidence is attached to the release; stg configuration is environment-isolated and its smoke check passes. |
| Production promotion | Explicit human approval; production NFR, security, retention, backup and rollback readiness evidence is reviewed. |

## Deployment, Rollback and Secrets

For dev, publish immutable Lambda versions and move the live alias after deployment smoke checks. For a production application release, use a small canary shift through the alias before full traffic; retain the prior version for rollback. Keep API and data changes backward compatible using expand/contract steps. If a deployed legacy wallet-keyed payload layout exists, use the quiesced additive migration and count/balance/history checks in infrastructure-specification.md before enabling the new writer. Do not reset balances or discard old transfers. After migration, the rollback candidate must understand canonical Transactions and its lookup entries; a legacy payload-only writer is not a valid rollback. Redeploying code does not restore lost data; disposable dev may be rebuilt only by an explicit engineer decision and must recreate fixtures through supported setup.

GitHub OIDC roles are separate by repository and environment, restricted to the repository/ref and required actions. The dev deploy role may update only dev stacks. MoneyApi's execution role has only the table actions needed by Ledger and WalletDirectory on this environment's three named table resources; the platform edge has no table access. Logical data-access ports keep profile and money ownership separate inside the service. Both runtimes have read-only access to the shared current/previous correlation HMAC secret. Test-user passwords are fetched from Secrets Manager at execution time and are not passed as command-line arguments or printed in CI output. Notification email, hostnames, issuer, audience and client IDs are deployment inputs, not checked-in constants. Keep credentials and personal attributes out of workflow artifacts and alarm text.

No pipeline result, deployed resource, load result or alarm delivery is claimed by this design. Build and Test records actual evidence after implementation.

Performance reports wait at most two minutes after the run for telemetry reconciliation. CloudFront delivery remains best effort at 100% sampling; an incomplete run is reported as such and blocks release acceptance. Never discard a missing/cold/slow sample, substitute adapter duration, or resubmit an uncertain financial attempt to obtain a cleaner measurement. The slow alarm consumes the observed, deduplicated five-minute public-duration windows defined in monitoring-design.md, with collection lag and coverage limitations displayed; it is not a complete-accounting guarantee outside the controlled run.

## Provisioning and Provider Gates

Before any deploy or asset publication, require explicit cost clearance; current instruction is no cost. Use a non-root short-lived deployment role, never the earlier inspection identity. External DNS must supply actual controlled hostname/validation records and issued custom certificate with TLS1.2 rejection probes; hostedZoneId is not required or purchased. The P7 earlier-code invalidation capability is unverified and blocks full identity release if unmet; no pre-confirmation trigger is assumed. Update the existing CDK native GetUser/external-DNS path in Code Generation, then actual bundle/synth/nag/diff and origin-header delivery proof. Three repo SHAs and independent API/iOS/Android fixtures remain mandatory; fake device journeys do not pass scripts/verify-dev.sh.
