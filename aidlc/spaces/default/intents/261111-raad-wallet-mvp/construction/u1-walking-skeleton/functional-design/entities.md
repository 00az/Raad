# Entities: U1 Walking Skeleton

Conversation language: English.

This document defines the entities introduced in U1. All amounts are stored and calculated as whole halalas (1 SAR = 100 halalas); no decimal or floating-point representation is used at any boundary (project rules).

```yaml
entities:

  - name: Wallet
    description: >
      A single SAR wallet belonging to one confirmed account holder.
      Opened automatically through the safety-net entry point at the holder's
      first authenticated money request; never opened twice for the same holder.
    owner_component: Ledger
    attributes:
      - name: wallet_id
        type: opaque identifier
        required: true
        unique: true
        description: Stable, opaque wallet identifier. Never the holder's email address.
      - name: owner_id
        type: opaque identifier
        required: true
        unique: true
        description: >
          The confirmed account holder this wallet belongs to.
          One wallet per owner; uniqueness is enforced even under simultaneous
          first-request races.
      - name: balance_halalas
        type: non-negative integer
        required: true
        min: 0
        description: >
          Current balance in whole halalas. Never negative. Updated atomically
          with any transfer that affects this wallet.
      - name: opening_balance_halalas
        type: non-negative integer
        required: true
        description: >
          The balance credited when the wallet was first created (100,000 halalas for every
          new wallet in U1). Immutable after creation. Stored to make the "credited once"
          invariant of BR2.1 directly verifiable in the record.
      - name: opened_at
        type: UTC timestamp
        required: true
        description: When the wallet was created. Supports ordering and audit.
    entity_constraints:
      - Exactly one Wallet per owner_id. Concurrent first requests for the same
        owner_id must result in one Wallet, not two.
      - balance_halalas is always >= 0. No operation may reduce it below zero.
    relationships:
      - entity: Transfer
        cardinality: one-to-many
        direction: Wallet -> Transfer
        description: A Wallet has zero or more completed Transfers as sender or receiver.
      - entity: WalletHolder
        cardinality: many-to-one
        direction: Wallet -> WalletHolder
        description: Each Wallet is owned by exactly one WalletHolder.

  - name: Transfer
    description: >
      A completed, atomic movement of whole halalas from one wallet to another.
      A Transfer is only created when both the debit and credit succeed together.
      Failed attempts leave no Transfer record.
    owner_component: Ledger
    storage: Dedicated Transactions table; one immutable row per transfer_id (C1 transferId), never keyed by a wallet ID.
    attributes:
      - name: transfer_id
        type: UUID
        required: true
        unique: true
        description: Stable reference generated by Ledger. Returned to the caller on success.
      - name: sender_wallet_id
        type: Wallet reference
        required: true
        description: The wallet debited.
      - name: recipient_wallet_id
        type: Wallet reference
        required: true
        description: The wallet credited. Must differ from sender_wallet_id.
      - name: amount_halalas
        type: positive integer
        required: true
        min: 1
        description: >
          Amount transferred, in whole halalas. U1 carries no upper limit; that
          constraint is introduced in U2 (amount limits, 100–50000 halalas).
      - name: reference
        type: string
        required: true
        unique: true
        min_length: 1
        max_length: 64
        description: >
          Human-readable transfer reference generated by Ledger (e.g. "TXN-20261112-00001").
          Distinct from transfer_id; returned to callers in the success response and in
          history entries. Maps to the C1 contract's `reference` field on TransferResult
          and TransferListItem.
      - name: completed_at
        type: UTC timestamp
        required: true
        description: When the transfer was committed. Used for ordering history entries.
    entity_constraints:
      - sender_wallet_id != recipient_wallet_id (self-transfer not allowed; enforced in U2).
      - amount_halalas >= 1 (positive integer; U2 adds the upper limit and minimum floor).
      - Transfer is immutable once created.
      - The transfer row and both wallet balance changes commit atomically or none commit.
      - sender_wallet_id and recipient_wallet_id support history selection; they are not the transaction primary key. U2 adds their history indexes and paging to this same table.
    relationships:
      - entity: Wallet
        cardinality: many-to-one
        direction: Transfer -> Wallet (sender)
        description: Each Transfer has exactly one sender Wallet.
      - entity: Wallet
        cardinality: many-to-one
        direction: Transfer -> Wallet (recipient)
        description: Each Transfer has exactly one recipient Wallet.

  - name: WalletHolder
    description: >
      A confirmed account holder who has (or will have) a wallet. Created
      by WalletDirectory during U1's authenticated PUT /wallet setup, using the
      verified profile after Ledger opens or reads the wallet. U2 adds the
      account-confirmation event entry point. Identified by a normalized email
      address (Unicode whitespace trim, NFC, lowercase).
    owner_component: WalletDirectory
    attributes:
      - name: holder_id
        type: opaque identifier
        required: true
        unique: true
        description: >
          Opaque, stable identifier for this holder. Used by Ledger as owner_id.
          Not the email address.
      - name: email_normalized
        type: string (email)
        required: true
        unique: true
        description: >
          The holder's email address, normalized: trimmed of surrounding
          whitespace and lowercased. Uniqueness is enforced; no two
          WalletHolder records may share the same normalized email.
      - name: display_name
        type: string
        required: true
        description: The holder's chosen display name. Used in transfer history entries.
    entity_constraints:
      - email_normalized is unique across all WalletHolder records.
      - email_normalized is derived before validation by trimming Unicode whitespace, normalizing to NFC, then locale-independent lowercasing (C1).
      - display_name is non-empty.
    relationships:
      - entity: Wallet
        cardinality: one-to-one
        direction: WalletHolder -> Wallet
        description: >
          Each WalletHolder owns at most one Wallet in U1. The Wallet is
          created lazily on the holder's first authenticated money request.
```

## Entity Summary

U1 introduces three entities owned by the backend components.

**Wallet** (Ledger) holds a balance in whole halalas and belongs to exactly one holder. Its invariant — balance never below zero, one wallet per owner even under concurrent requests — is what makes the money properties testable with the Hypothesis property test.

**Transfer** (Ledger) is an immutable record of a completed atomic movement. A transfer that fails mid-flight creates no record. U1 carries no upper or lower amount limits (those come in U2); the only constraint here is that the amount is a positive integer of halalas.

Its dedicated `Transactions` table is keyed by `transfer_id` (the API's `transferId`). Wallet IDs remain references on the row. Wallet records retain current balances. U1 introduces no `TransferRequest` or saved key-to-outcome record; U2 introduces those and includes a successful outcome in the atomic transfer write.

**WalletHolder** (WalletDirectory) maps a normalized email address to an opaque holder ID and a display name. Normalization (trim Unicode whitespace, NFC, lowercase) is applied at write time and again before validation and every lookup, so `A@X.com ` and `a@x.com` resolve to the same holder.
